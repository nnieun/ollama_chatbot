# PRD: Local LLM Chat 프론트엔드

## 1. 개요

Vite 기본 화면을 `docs/ui설계도.png`의 Local LLM Chat 화면으로 교체한다. 사용자는 좌측 설정 패널에서 모델 및 생성 옵션을 지정하고, 우측 대화 화면에서 로컬 LLM과 대화한다.

설계 기준 이미지는 프로젝트에 존재하는 `docs/ui설계도.png`이다. 요청에 언급된 `ui설계.jpg` 파일은 프로젝트에서 확인되지 않았다.

## 2. 목표

- 설계도의 화면 구조와 시각적 계층을 React 프론트엔드에 반영한다.
- 확인된 기존 백엔드 API를 사용하여 모델 목록 조회 및 채팅 요청을 지원한다.
- React와 JavaScript만 사용하며, TypeScript를 도입하지 않는다.
- 기존 API 계약·백엔드·인프라를 변경하지 않는다.

## 3. 사용자 스토리

- 사용자는 사용할 로컬 LLM 모델을 선택하고 싶다.
- 사용자는 시스템 프롬프트와 생성 옵션을 조정하고 싶다.
- 사용자는 질문을 입력하여 로컬 LLM의 응답을 보고 싶다.
- 사용자는 현재 대화를 초기화하고 싶다.

## 4. 화면 구조

- 좌측: 모델 설정 패널
  - 모델 선택
  - 시스템 프롬프트
  - Temperature
  - Top P
  - Num Predict
- 우측 상단: 서비스 제목, 설명, 대화 초기화 버튼
- 우측 중앙: 대화 메시지 영역
- 우측 하단: 메시지 입력 영역 및 전송 버튼

## 5. `ui설계도.png`에서 확인된 UI 요구사항

- FR-001: 연한 회보라색 배경 위에 좌측 설정 사이드바와 우측 메인 대화 영역을 배치한다.
- FR-002: 설정 패널에는 `모델`, `시스템 프롬프트`, `Temperature: 0.7`, `Top P: 0.9`, `Num Predict` 요소를 표시한다.
- FR-003: 상단 헤더에 `Local LLM Chat`, `React + FastAPI + Ollama 기반 로컬 AI 채팅 앱`, `대화 초기화` 버튼을 표시한다.
- FR-004: 대화 영역에서 사용자 메시지는 우측의 파란색 말풍선으로, AI 응답은 좌측의 연한 보라색 카드로 표시한다.
- FR-005: 하단에 메시지 입력창, `Shift+Enter: 줄바꿈` 안내, `전송` 버튼을 표시한다.
- FR-006: 카드형 영역에는 둥근 모서리와 약한 그림자를 적용하고, 기존 CSS 토큰이 적합하면 우선 재사용한다.

## 6. 기능 요구사항

- FR-007: 화면 진입 시 모델 목록을 조회해 모델 선택 UI에 표시한다.
- FR-008: 사용자가 모델, 시스템 프롬프트, Temperature, Top P, Num Predict 값을 변경할 수 있어야 한다.
- FR-009: 사용자가 메시지를 입력하고 전송할 수 있어야 한다.
- FR-010: 채팅 요청에는 현재 입력된 메시지와 설정값을 사용한다.
- FR-011: 확정된 채팅 응답 계약에 따라 AI 응답을 대화 영역에 표시한다.
- FR-012: `대화 초기화` 동작은 현재 화면의 대화 메시지를 초기화한다.
- FR-013: 전송 중인 상태를 사용자에게 표시하고, 중복 전송을 방지한다.

## 7. API 연동 요구사항

- FR-014: 모델 목록은 기존 `GET http://localhost:8000/models`를 사용한다.
- FR-015: 채팅 요청은 기존 `POST http://localhost:8000/chat`를 사용한다.
- FR-016: `POST /chat`에는 기존 요청 필드인 `message`, `model`, `system_prompt`, `temperature`, `top_p`, `num_predict`만 전송한다.
- FR-017: API URL, HTTP 메서드, 요청·응답 필드, 인증 방식을 변경하지 않는다.
- FR-018: 인증 정보나 Authorization 헤더는 현재 확인되지 않았으므로 임의로 추가하지 않는다.

`POST /chat`의 응답은 선언 모델에서 `message`를 요구하지만 실제 반환 코드에서는 `ai_message`를 반환해 불일치가 확인되었다. 이 필드는 확정 전까지 구현 대상으로 간주하지 않는다.

## 8. 로딩, 빈 결과, 오류 상태

설계도에서 확인되지 않아 다음 상태의 UI·문구·동작은 승인 전 구현하지 않는다.

- 모델 목록 로딩·빈 결과·오류
- 채팅 전송 중 상태
- 채팅 요청 실패 및 재시도
- 빈 대화 초기 상태
- 서버 연결 불가 상태

## 9. 접근성 요구사항

- FR-019: 모든 입력 컨트롤은 식별 가능한 레이블을 제공한다.
- FR-020: 버튼과 입력 요소는 키보드로 조작할 수 있어야 한다.
- FR-021: 비활성화된 컨트롤은 프로그램적으로 상태를 전달해야 한다.
- FR-022: 메시지 주체와 상태를 색상만으로 구분하지 않는다.

## 10. 반응형 요구사항

설계도는 데스크톱 화면만 제공한다. 사이드바 축소·재배치, 모바일 입력 영역, 메시지 카드 폭 등 반응형 동작은 확인되지 않았으며 승인 전 구현하지 않는다.

## 11. 테스트 가능한 인수 조건

- AC-001: FR-001~FR-006 — 화면에 좌측 설정 패널, 헤더, 대화 영역, 입력 영역이 설계도와 동일한 계층으로 표시된다.
- AC-002: FR-002 — 모델 선택, 시스템 프롬프트, Temperature, Top P, Num Predict 입력 요소가 표시된다.
- AC-003: FR-007, FR-014 — 모델 목록 API의 성공 응답이 모델 선택 UI에 반영된다.
- AC-004: FR-008~FR-010, FR-016 — 변경된 설정값과 메시지가 채팅 요청에 사용된다.
- AC-005: FR-011, FR-015 — 응답 필드 계약이 확정된 뒤 AI 응답이 대화 영역에 표시된다.
- AC-006: FR-012 — 대화 초기화 시 현재 대화 메시지가 화면에서 제거된다.
- AC-007: FR-013 — 요청 중에는 중복 전송이 방지되고 진행 상태가 표시된다.
- AC-008: FR-019~FR-022 — 키보드 조작과 접근 가능한 레이블을 제공한다.

## 12. Non-Goals

- TypeScript 도입
- 백엔드 코드 변경
- API 계약 변경
- 데이터베이스 변경
- 승인되지 않은 패키지 설치
- 이미지에 없는 기능 추가
- 관련 없는 리팩터링
- 인증·권한 체계의 신규 도입
- 설계도에 없는 반응형·오류·로딩 동작의 임의 결정

## 13. 기술적 제약

- React + JavaScript만 사용한다.
- 컴포넌트는 기존 규칙에 따라 `.jsx` 또는 `.js`로 작성한다.
- `.ts`, `.tsx`, `tsconfig.json`을 생성하거나 수정하지 않는다.
- TypeScript 관련 패키지를 추가하지 않는다.
- 외부 데이터의 런타임 검증 방식은 현재 확인되지 않았다.
- 신규 패키지는 승인 전 설치하지 않는다.
- React 또는 외부 라이브러리 API 사용 시 설치 버전을 확인하고 Context7의 JavaScript 문서를 우선 확인한다.

## 14. Open Questions

1. `POST /chat` 응답의 실제 메시지 필드는 `message`와 `ai_message` 중 무엇으로 확정되는가?
2. 모델 목록과 채팅 요청의 로딩·빈 결과·오류 UI 및 문구는 무엇인가?
3. `Shift+Enter` 외 Enter 키의 전송 동작은 무엇인가?
4. 모바일·태블릿 반응형 레이아웃은 어떻게 동작해야 하는가?
5. 외부 API 응답의 런타임 검증이 필요한가? 필요하다면 패키지 도입은 별도 승인 대상이다.
6. Context7이 연결된 세션에서 React 19.3.0과 Vite 8.3.0의 JavaScript 사용법을 확인한 뒤 구현을 진행해도 되는가?

## 15. 성공 조건

- 설계도에서 확인되는 화면 구조·텍스트·시각적 계층이 구현에 반영된다.
- 모델 조회와 채팅 요청은 확정된 기존 API 계약만 사용한다.
- TypeScript 파일·설정·패키지가 추가되지 않는다.
- 승인된 범위 외의 백엔드, 데이터베이스, 인프라, API 계약 변경이 없다.
- 인수 조건이 실제 검증 결과와 함께 충족되었다고 보고된다.
